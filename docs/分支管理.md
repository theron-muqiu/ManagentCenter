# 分支与版本管理

## 长期分支

| 分支 | 用途 | 合并方向 |
| --- | --- | --- |
| `main` | 已验证、可发布的稳定版本 | 接收 `release/*`、`hotfix/*` |
| `develop` | 日常开发与功能集成 | 接收 `feature/*`、`fix/*` |

首次提交作为两个长期分支的共同起点，版本标签为 `v0.1.0`。

## 工作流程

1. 从最新 `develop` 创建 `feature/功能名称` 或 `fix/问题名称`，每个分支聚焦一项修改。
2. 完成实现与相关验证后，通过 Pull Request 合并到 `develop`，说明修改目的、影响范围与验证结果。
3. 准备发布时，从 `develop` 创建 `release/版本号`，只修复发布阻塞问题和更新版本说明。
4. 发布验证通过后合并到 `main`，创建版本标签，并将发布修复同步回 `develop`。
5. 线上紧急修复从 `main` 创建 `hotfix/问题名称`，验证后合并到 `main` 并同步回 `develop`。
6. 合并完成后删除临时分支。禁止强制推送长期分支，避免改写公共历史。

提交说明以中文为主，建议使用 `类型: 中文说明`，例如 `feat: 增加用户角色分配`、`fix: 修复日志日期筛选`、`docs: 更新部署说明`。

涉及前端修改时执行相关组件测试与生产构建；涉及后端业务时执行相关测试，集成测试只使用专用测试数据库和 Redis。真实密码、Token、本地环境文件和构建产物不得提交。

## GitHub 分支保护建议

建议对 `main` 和 `develop` 启用 Pull Request 合并、禁止强制推送及删除，并在配置 CI 后要求对应检查通过。本文是协作约定，仓库服务端保护规则需在 GitHub 设置中实际启用；首次发布不表示已配置保护规则。
